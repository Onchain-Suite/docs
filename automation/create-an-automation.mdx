An automation is a **trigger** (the thing that starts it) plus a **flow** (what happens next). You build both on a visual canvas: drag in blocks, connect them, and publish. This page walks through building one, the blocks you can use, and the publish step that actually makes it live.

## Build it

<Steps>
  <Step title="Start from a play, or from scratch">
    Forking a [built-in play](/automation/overview) gives you a working trigger and flow as a draft you own. Starting blank gives you an empty canvas.
  </Step>
  <Step title="Configure the trigger">
    For a business preset (**Token acquired**, **Swap completed**, **Liquidity added**, and the rest), you supply just one thing: the **token or contract** to watch. The on-chain detail is set for you. Only the generic **On-chain event** trigger asks you to name a raw event. See [Triggers and Conditions](/automation/triggers-and-conditions).
  </Step>
  <Step title="Lay out the flow">
    Add action, wait, and branch blocks and connect them in order. The flow runs left to right, following the connections out of the trigger.
  </Step>
  <Step title="Validate">
    Validation flags blocking errors, which you must fix, and softer warnings, which you can leave. It won't let you publish something broken.
  </Step>
  <Step title="Preview">
    Preview estimates how many wallets currently match the trigger, with sample profiles. Run this before publishing. **A trigger matching zero wallets is the most common cause of a silent automation.**
  </Step>
  <Step title="Publish">
    Publishing creates the live version. Without it, nothing runs (more on this below).
  </Step>
</Steps>

## The building blocks

Eleven blocks make up a flow. The messaging blocks reach the contact; the rest shape the flow, organize your audience, or call your own systems.

| Block | What it does |
| --- | --- |
| **Send email** | Email the contact from a template. |
| **Send in-app** | Push an in-app notification to the contact's wallet. |
| **Wait** | Pause the flow for a set time, or until the contact does something. |
| **Branch** | Split the flow down different paths based on a condition. |
| **A/B split** | Randomly split contacts into weighted variants, for a test or a holdout. |
| **Add tag** | Put a tag on the contact. |
| **Remove tag** | Take a tag off the contact. |
| **Add to list** | Add the contact to an audience list. |
| **Remove from list** | Take the contact off an audience list. |
| **Launch campaign** | Fire a campaign you've already built. |
| **Call a webhook** | Ping your own system (for developers). |

### Messaging blocks

**Send email**, **Send in-app**, and **Launch campaign** all send to **the contact who triggered the flow** by default. You can also aim them at a specific list of wallets, or a whole segment. Content is personalized per recipient, so an in-app push supports the same merge variables as email, like `{{ greeting_name }}`.

- **Send email** uses a saved template plus a subject line (required, so it lands well in the inbox).
- **Send in-app** uses a title and body, with an optional button (give it both a label and a link for the button to show).
- **Launch campaign** kicks off a campaign you've already built, aimed at the recipient.

### Wait

Pause before the next step in one of two ways:

- **For a set time**, a number of seconds, minutes, hours, or days, or "until 9:00am in a timezone."
- **Until the contact does something**, hold them here until they enter a segment, submit a form, open an email, or a matching on-chain event fires, with a timeout path if it never happens.

Waiting contacts are parked and picked back up when the time comes, so a long wait costs you nothing while it sits.

### A/B split

Randomly send contacts down two or more paths, each with a weight you set (50/50 by default). Use it to test two messages against each other, or to hold a group back as a control:

- **Weights are relative**, so 70/30 sends roughly seven in ten down the first path.
- **A variant with no path out is your holdout**: contacts assigned to it simply stop, giving you an untouched control group to compare against.
- **Assignment is stable**, a contact keeps the same variant even if the flow retries, so your test stays clean.

### Tags and lists

Four blocks keep your audience organized as contacts move through a flow:

- **Add tag** and **Remove tag** put a tag on the contact or take it off (one or several at once). Handy for marking who's been through a flow so you can segment or suppress on it later. Removing a tag the contact doesn't have is simply a no-op.
- **Add to list** and **Remove from list** move the contact in or out of an audience [list](/audience/segments). Adding to a list can itself start a "joined a list" automation (loops are prevented), so lists are a clean way to hand a contact from one flow into another. Removing from a list is the way back out.

### Call a webhook (for developers)

The webhook block pings one of your own endpoints partway through a flow, so your systems can react to what happened. It's the one developer-flavored block: it needs a public `https` URL, and it hands your endpoint the contact's context. You can add a signing secret so your receiver can confirm the call really came from us. The full detail is in [Webhooks](/api/webhooks). This block sends **out**; to start an automation from your own system, see [Contract-Based Flows](/automation/contract-based-flows).

## Drafts and validation

The builder keeps your **work-in-progress draft** separate from the **saved flow**, so you can leave a block half-finished and come back to it. Saving to the main flow validates first, and a few things block a save: an empty flow, no trigger, an email step with nothing to send, a wait with no duration, or a branch with only one path out. A block that isn't connected to anything is a warning, not an error, the flow still publishes, but that block never runs.

## Publish

<Warning>
**Publishing is what makes an automation run.** The runtime executes the most recent *published* version of your flow. Setting an automation to `active` without publishing produces one that matches events, creates entries, and does nothing, the hardest failure to spot, because it looks live and the entry count climbs.

Publish after every change you want live. Saving the flow is not the same as publishing.
</Warning>

## When a step has trouble

Steps retry automatically a few times before giving up, and each step only re-runs the one that failed, not the ones before it, so nobody gets a duplicate email on a retry. Different steps handle trouble differently:

- **Send email** skips, and the flow moves on, if your sending is paused or every recipient is suppressed. It only retries when some recipients exist but the sends error out.
- **Send in-app** quietly drops wallets with no in-app session. It only fails if there's nobody left to send to.
- **Launch campaign, add tag, and webhook** retry, then give up if they keep failing.

## Watching an entry

Every contact that enters an automation is an **entry**, and each entry records what happened as it moved through the flow. This is how you answer "did this fire, and where did it stop." An entry is running, waiting (paused on a wait), completed, or failed, and its history shows when it was created, which steps it reached, which ran, and which were skipped and why (for example "sending paused" or "everyone suppressed").

When an email step sent nothing, check for a skip reason before assuming the trigger is broken. When an automation finishes, it also emits an `automation.completed` [webhook event](/api/webhooks) your systems can subscribe to.

<Note>
Automation stats (entries, conversions, revenue) are derived from send and delivery records. "Entries" counts trigger matches; conversion and revenue are inferred from event names and metadata, so treat them as directional rather than as an accounting source.
</Note>

## Best practices

- One trigger, one outcome. Add branches only after the primary path is verified.
- Preview before publishing so you know the trigger matches a non-zero audience.
- Name automations after trigger plus action, "Mint → welcome series" beats "Automation 3".
- Avoid overlapping automations targeting the same wallets on the same event.
- Test with a real event, then check the entry's history to confirm each step fired.
