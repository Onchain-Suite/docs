An automation is a trigger plus a flow graph. This page walks through building one, the node types available, and the publish step that actually makes it live.

## Build it

<Steps>
  <Step title="Start from a play, or from scratch">
    Forking a [built-in play](/automation/overview) gives you a working trigger and flow as a draft you own. Starting blank gives you an empty graph.
  </Step>
  <Step title="Configure the trigger">
    Pick the event type and narrow it with a chain, contract, event names, and payload filters. See [Triggers and Conditions](/automation/triggers-and-conditions).
  </Step>
  <Step title="Lay out the flow">
    Add action, wait, and branch nodes, and connect them with edges. Execution follows edges from the trigger node.
  </Step>
  <Step title="Validate">
    Validation reports blocking errors and non-blocking warnings. Fix the errors.
  </Step>
  <Step title="Preview">
    Preview estimates how many wallets currently match the trigger, with sample profiles. Run this before publishing. A trigger matching zero wallets is the most common cause of a silent automation.
  </Step>
  <Step title="Publish">
    Publishing creates the version the runtime executes. Without it, nothing runs.
  </Step>
</Steps>

## Node types

Seven node types are available. Each node's config lives in its `data` object.

| Type | Category | What it does |
| --- | --- | --- |
| `send_email` | Messaging | Send an email to the recipient |
| `send_inapp` | Messaging | Send an in-app push to the recipient |
| `dispatch_campaign` | Messaging | Launch a prepared campaign at the recipient |
| `wait` | Flow control | Pause the flow for a delay |
| `branch` | Flow control | Route the entry down different paths |
| `add_tag` | Audience | Tag the contact |
| `webhook` | Integrations | Call your endpoint |

<Note>
When the visual builder saves a node, the canonical type is in `data.actionType` while `node.type` holds the builder's own renderer key (like `"inapp"`). The runtime reads `data.actionType` first, so in hand-authored JSON either set `data.actionType` to the type in the table above, or set `node.type` to it directly, as the examples here do.
</Note>

### Messaging nodes

All three messaging nodes choose recipients with `recipientMode` (`triggering_profile`, the default, or `wallet_list` with a `walletAddresses` array). Content is merge-rendered per recipient, so `send_inapp` supports the same variables as email, such as `{{ greeting_name }}` and `{{ wallet_short }}`.

**`send_email`** reads `templateId` (loads a template) or inline `subject` and `body`, plus an optional `senderEmail` override. It needs a template, a subject, or a body; with none it fails validation.

**`send_inapp`** reads `title` and `body` (defaulting to generic text if absent), and optional `ctaLabel` and `ctaUrl`. The button renders only when both CTA fields are present. It can also draw content from a `campaignId`.

**`dispatch_campaign`** reads `campaignId` and launches that prepared campaign at the recipient.

### Waits

The simplest form is `seconds`:

```json
{ "id": "wait_30m", "type": "wait", "data": { "seconds": 1800 } }
```

You can also use `minutes`, `hours`, or `days`, or an amount-and-unit pair:

```json
{ "data": { "amount": 2, "unit": "hours" } }
```

Two more forms are available:

```json
// Wait until the next occurrence of a local wall-clock time
{ "data": { "until": "09:00", "timezone": "Africa/Lagos" } }

// Explicit milliseconds
{ "data": { "delayMs": 90000 } }
```

The unit defaults to **minutes** when omitted, and any delay is clamped to a minimum of one second. A waiting entry is scheduled and resumed later, so it doesn't hold a worker open, and a stranded resume is recovered if the queue restarts.

### Tags

```json
{ "id": "tag_minter", "type": "add_tag", "data": { "tag": "minted-2026" } }
```

A `tags` array is also accepted for applying several at once.

<Note>
There is no `remove_tag` action. A graph containing one fails validation with `UNSUPPORTED_NODE_TYPE`.
</Note>

### Outbound webhooks

The `webhook` node posts to your endpoint mid-flow. Method may be `POST` (default), `PUT`, or `PATCH`.

```json
{
  "id": "notify_backend",
  "type": "webhook",
  "data": {
    "url": "https://api.example.com/hooks/onchain-suite",
    "method": "POST",
    "headers": { "X-Api-Key": "..." },
    "payload": { "source": "automation" }
  }
}
```

Your endpoint receives:

```json
{
  "organizationId": "...",
  "automationId": "...",
  "entryId": "...",
  "context": {
    "email": "user@example.com",
    "walletAddress": "0xabc...",
    "contactId": "...",
    "lastInapp": { }
  },
  "source": "automation"
}
```

Any response of 400 or above counts as a failure and is retried up to 5 times with exponential backoff, then dead-lettered. Requests time out after 10 seconds.

<Warning>
The URL must be a **public** `https` (or `http`) endpoint. URLs pointing at private networks (`localhost`, private IP ranges, or a cloud metadata address) are rejected when you save the node, and again at send time, including via redirects. It also can't embed credentials (`user:pass@host`). This is an anti-SSRF safeguard; host your webhook on a reachable public address.
</Warning>

<Warning>
Keys in your `payload` are merged **last**, so a payload key named `organizationId`, `automationId`, `entryId`, or `context` will overwrite the platform's own value. Namespace your custom fields.
</Warning>

<Note>
This node sends webhooks **out**. There is no inbound webhook trigger. To start an automation from your own system, call the ingest API described in [Contract-Based Flows](/automation/contract-based-flows).
</Note>

## The flow graph

The graph is plain JSON: a list of nodes and a list of edges.

```json
{
  "nodes": [
    {
      "id": "trigger_holder_acquired",
      "type": "holder_acquired",
      "position": { "x": 120, "y": 140 },
      "data": {
        "chain": "base-mainnet",
        "contractAddress": "0xYourCollection",
        "eventNames": ["Transfer"],
        "filters": [
          { "path": "from", "operator": "eq", "value": "0x0000000000000000000000000000000000000000" }
        ]
      }
    },
    {
      "id": "inapp_welcome",
      "type": "send_inapp",
      "position": { "x": 420, "y": 140 },
      "data": {
        "title": "Welcome onchain",
        "body": "Thanks for minting. Here's what to do next.",
        "recipientMode": "triggering_profile"
      }
    },
    {
      "id": "wait_1h",
      "type": "wait",
      "position": { "x": 720, "y": 140 },
      "data": { "seconds": 3600 }
    },
    {
      "id": "email_welcome",
      "type": "send_email",
      "position": { "x": 1020, "y": 140 },
      "data": {
        "templateId": "tpl_welcome",
        "subject": "Welcome to the community",
        "recipientMode": "triggering_profile"
      }
    }
  ],
  "edges": [
    { "id": "e1", "source": "trigger_holder_acquired", "target": "inapp_welcome" },
    { "id": "e2", "source": "inapp_welcome", "target": "wait_1h" },
    { "id": "e3", "source": "wait_1h", "target": "email_welcome" }
  ]
}
```

Edges pointing at nodes that don't exist are dropped silently on save.

## Drafts and validation

The builder keeps a **draft graph** and a **saved graph** separately. Draft saves are unvalidated, so you can leave a node half-configured and come back to it. Saving to the main graph validates first.

Blocking errors you'll encounter:

| Code | Meaning |
| --- | --- |
| `EMPTY_FLOW` | No nodes |
| `MISSING_TRIGGER` | No trigger node |
| `UNSUPPORTED_NODE_TYPE` | Node type isn't one of the seven |
| `INVALID_EMAIL_CONFIG` | `send_email` has no template |
| `INVALID_INAPP_RECIPIENTS` | Wallet-list mode with no wallets |
| `INVALID_WAIT_CONFIG` | Missing or non-positive duration |
| `INVALID_BRANCH_CONFIG` | Fewer than two outgoing edges |
| `INVALID_WEBHOOK_CONFIG` | Missing, malformed, or private/blocked URL |
| `INVALID_TAG_CONFIG` | Empty tag |
| `INVALID_EDGE` | Edge references a missing node |

`DISCONNECTED_NODES` is a warning, not an error. The graph still publishes, but the orphaned nodes never execute.

## Publish

<Warning>
**Publishing is what makes an automation run.** The runtime executes the most recent *published version* of the graph. Setting status to `active` without publishing produces an automation that matches events, creates entries, and does nothing. It's the hardest failure mode to spot, because the automation looks live and entry counts climb.

Publish after every change you want live. Saving the graph is not publishing.
</Warning>

## Retries and failures

Each step retries up to 3 times with exponential backoff. After the final attempt the entry is marked `failed` and recorded as a dead letter with the error.

Each side-effecting node claims itself before it runs, so a retried entry re-runs only the node that failed, not the ones that already succeeded. This gives you effectively exactly-once delivery per node even across retries.

Nodes fail in different ways:

| Node | On trouble |
| --- | --- |
| `send_email` | **Skips** (flow continues) if sending reputation is blocked or every recipient is suppressed. Fails and retries only if some recipients exist but every send errors. |
| `send_inapp` | Wallets with no in-app session are filtered out. Fails only if there are zero wallet recipients. |
| `webhook`, `add_tag`, `dispatch_campaign` | Fail and retry, then dead-letter. |

## Watching an entry

Every contact that enters an automation is an **entry**, and each entry records events as it moves through the flow. This is how you answer "did this fire, and where did it stop."

An entry is `running`, `waiting` (paused on a `wait`), `completed`, or `failed`. Its events include:

| Event | Meaning |
| --- | --- |
| `trigger_received` | The entry was created from a matching event. |
| `node_entered` | Execution reached a node. |
| `action_executed` | A node ran, with detail like recipient count and delivery IDs. |
| `node_skipped` | A node was reachable but declined to run, with a reason such as `reputation_blocked` or `all_suppressed`. |
| `wait_scheduled` | A `wait` node scheduled a resume. |
| `dead_lettered` | The entry failed terminally after retries. |

When an email step produces no sends, look for `node_skipped` and its reason before assuming the trigger is broken. When an automation completes, it also emits a public `automation.completed` [webhook event](/api/webhooks) you can subscribe to.

<Note>
Automation stats (entries, conversions, revenue, time-series, paths) are derived from send and delivery records, so "entries" counts trigger matches. Conversion and revenue are inferred from event names and metadata, so treat them as directional rather than as an accounting source.
</Note>

## Best practices

- One trigger, one outcome. Add branches only after the primary path is verified.
- Preview before publishing so you know the trigger matches a non-zero audience.
- Name automations after trigger plus action, "Mint → welcome series" beats "Automation 3".
- Avoid overlapping automations targeting the same wallets on the same event.
- Test with a real event, then check entry events to confirm each node fired.
