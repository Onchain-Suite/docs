Use cases are complete playbooks: a goal, the dashboard setup, the code where you need it, and how to measure the result. They're split by audience, because a Web3 protocol and a Web2 SaaS run the same plays with different identities and channels.

<Note>
**Web3 or Web2?** Web3 teams work from the **wallet**: identify by wallet, and reach people **in-app** and by push where there's no email on file. Web2 teams work from **email**: identify people by email, send email campaigns and automations. Most plays exist in both tracks. The Web3 version swaps the wallet for the email, and an in-app message for an email send where the platform can't email.
</Note>

## The shape of every playbook

Each page follows the same structure, so you can scan to the part you need:

1. **Goal and outcome**, what you're building and what it should move.
2. **Who it's for**, Web3, Web2, or both.
3. **Prerequisites**, what to set up first.
4. **Build it**, numbered steps mixing the dashboard and code.
5. **Test**, how to prove it works before going live.
6. **Measure**, what to watch afterward.
7. **Variations**, common tweaks.

Code examples come in **curl, Python, TypeScript, PHP, and Go**, so whoever wires it up can copy the one they need.

<Note>
**Organize as you go.** Any playbook that sends an event can drop the contact into a tag or list at the same time, just add `tags` or `addToList` to the event. See [Tags, lists, and segments](/integrations/tags-lists-segments).
</Note>
