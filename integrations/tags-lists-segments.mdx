Tags, lists, and segments are how you group contacts so a campaign or automation can target them. They overlap, so here's the plain version and, below, every way to put a contact into one.

## The three, in plain terms

- **Tag**, a free-form label on a contact (`vip`, `beta`, `nft-holder`). A contact can carry many. You create a tag just by using it.
- **List**, a named group a contact belongs to, backed by a tag. Imports land in a list, and capture forms add to a bound list. List names are unique per workspace. A list is usually what you send a campaign to. Every list has an **ID** you can copy from **Audience → Lists** (the row's ⋯ menu → **Copy list ID**) to use as `listIds` on an event or in the API.
- **Segment**, a saved audience definition. Either a **fixed set** (materialized from a query or an [Agentic Chat](/intelligence/agentic-chat) answer) or a **rule** that re-evaluates over time. Segments feed campaigns and automations too.

<Note>
Lists and segments overlap a lot. Reach for a **list** for "people I put here" (imports, form sign-ups, an event that says where they belong), and a **segment** for "people who match this" (a query or a rule).
</Note>

## Put a contact into a tag or list

Four ways, pick by where the decision is made.

### From an event, inline

Send `tags`, `listIds`, or `addToList` on a [custom event](/integrations/custom-events). Tags and unknown list names are created for you, and the change lands **before** automations run, so an automation on the same event can branch on it.

```bash
curl -X POST https://api.onchainsuite.com/api/v1/events \
  -H "Authorization: Bearer sk_live_…" \
  -H "Content-Type: application/json" \
  -d '{
    "event": "beta_joined",
    "contact": { "email": "alice@example.com" },
    "tags": ["beta"],
    "addToList": "Beta users"
  }'
```

Use this when the event itself tells you where the contact belongs. A list bound to a consent-required form still admits only consent-confirmed contacts, so you can't bypass double opt-in this way.

### From a capture form

A [capture form](/audience/capture-forms) applies its bound list and tags on confirmation, the consent-first way an email and a list membership arrive together.

### From an automation

Add an **Add tag**, **Remove tag**, **Add to list**, or **Remove from list** action to an [automation](/automation/create-an-automation). Use this when the decision depends on branching logic, a channel, what the contact did, or a wait.

### From Intelligence, as a segment

Save a [SQL or Reports result](/intelligence/reports-and-segments#save-as-a-segment), or an [Agentic Chat](/intelligence/agentic-chat) answer, as a **segment**. A query result can be keyed by a **wallet**, **email**, or **contact-id** column, so an email-only, Web2 cohort works too.

## Which one should I use?

- "This event means they belong here" → set it **inline on the event**.
- "They gave consent through a form" → the form's **bound list**.
- "It depends on branching or timing" → an **automation** action.
- "Everyone who matches this query or question" → a **segment**.

## Add contacts already in your audience

The ways above decide membership as a contact **arrives or acts**. To add contacts that are **already in your audience** — a backfill, or a hand-picked set — work from the list itself:

- **Dashboard** — open the list under **Audience → Lists** and add members, or select contacts in the audience table and choose **Add to list**.
- **API** — `POST /audience/segments/{listId}/members` with the contact ids (a list is a kind of segment, so the path says `segments`). Additive and idempotent, up to 1000 per call; it reports who actually joined versus who was already a member.

```bash
curl -X POST https://api.onchainsuite.com/api/v1/audience/segments/{listId}/members \
  -H "Authorization: Bearer <session token>" \
  -H "x-org-id: <your org id>" \
  -H "Content-Type: application/json" \
  -d '{ "profileIds": ["contact_abc", "contact_def"] }'
# → { "added": 2, "alreadyMembers": 0, "skipped": 0, "count": 2 }
```

<Note>
The audience API (`/audience/…`) uses your **dashboard session**, not a server `sk_` key — the `sk_` keys are for the ingest API (`/events`). Pass your active workspace as the `x-org-id` header.
</Note>

## Find, rename, or delete a list

From **Audience → Lists**, each row's ⋯ menu:

- **Copy list ID** — the handle you pass as `listIds` on an event or as `{listId}` in the API. `GET /audience/lists` returns every list with its ID and live member count.
- **Rename** — changes the display name; membership is unaffected.
- **Delete** — removes the list. Your contacts are **kept** by default (a list is a saved view, not the people in it); you can choose to delete the members too.

## Using them downstream

Tags, lists, and segments all target [campaigns](/campaigns/overview) and [automation triggers](/automation/triggers-and-conditions) (for example, "entered a segment" or "joined a list"). To take a contact out of a list, use the **Remove from list** action; there's no list-exit trigger, so removing someone won't start another flow.
